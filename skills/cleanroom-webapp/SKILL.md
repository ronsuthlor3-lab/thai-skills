# สร้างเว็บแอปของตัวเองแบบ clean-room (cleanroom-webapp)

สกิลนี้พาผู้ใช้จาก "อยากได้แอปแบบ X" ไปสู่เว็บแอปที่ **ทำงานคล้าย X แต่เป็นงานสร้างสรรค์ใหม่ของผู้ใช้เองทั้งหมด** ได้แก่ ชื่อใหม่ หน้าตาใหม่ และโค้ดที่เขียนใหม่ หลักคิดคือ ลิขสิทธิ์คุ้มครอง "การแสดงออก" (โค้ด ข้อความ ภาพ) แต่ไม่คุ้มครอง "ความคิด ขั้นตอน ระบบ วิธีใช้หรือทำงาน" (พ.ร.บ.ลิขสิทธิ์ 2537 ม.6 วรรคสอง [S-01]; เทียบ 17 U.S.C. §102(b) [S-07], Circular 61 [S-08])

**วันที่ตรวจแหล่ง: 2026-11-10** กฎหมายอาจแก้ไขหลังวันนี้ ให้บอกผู้ใช้ทุกครั้งที่ส่งมอบ

ไฟล์ประกอบ:
- `references/sources.md` — บัญชีแหล่ง S-01..S-10 และรายการที่ยืนยันไม่ได้ U-xx (รหัส [S-xx] ในไฟล์นี้หมายถึงไฟล์นั้น)
- `references/templates.md` — แม่แบบสเปกเชิงหน้าที่ ตารางความเป็นไปได้ บันทึกการออกแบบ README เต็ม (รวมส่วนแรงบันดาลใจ) ตัวอย่าง LICENSE MIT รายงานทดสอบ
- `examples/example-run.md` — ตัวอย่างการใช้สกิลกับ "แอปจดโน้ตแบบการ์ด" สมมติ

กติกาการอ้างอิง:
- **ข้อบังคับ** = มีมาตราและรหัสแหล่งที่ยืนยันแล้วรองรับ
- **ข้อบังคับ (คำแปล)** = อิงแหล่งสถานะ "บางส่วน" ให้บอกผู้ใช้ว่าเป็นคำแปลไม่เป็นทางการ
- **แนวปฏิบัติ** = วิธีทำงานที่ปลอดภัยกว่า แต่ไม่มีมาตรารองรับโดยตรง ห้ามพูดว่า "กฎหมายบังคับ"
- **ข้อบังคับของสกิล** = กติกาของสกิลนี้เอง ไม่ใช่กฎหมาย ห้ามพูดว่า "กฎหมายบังคับ"
- เรื่องใน U-xx ห้ามใช้เป็นเกณฑ์ ถ้าผู้ใช้ถามให้บอกว่ายืนยันไม่ได้

## เฟส 0 — คัดกรอง

### 0.1 ถามให้ครบ (ถามเฉพาะที่ขาด ไม่เกิน 5 ข้อในรอบแรก)
1. โปรแกรมต้นแบบชื่ออะไร เป็นเว็บ แอปมือถือ หรือโปรแกรมเดสก์ท็อป
2. อยากได้ส่วนไหนของมัน (ฟีเจอร์หลัก 3–5 อย่าง) และส่วนไหนไม่ต้องการ
3. จะใช้เองคนเดียว แจกฟรี หรือทำเชิงพาณิชย์
4. ข้อมูลต้องแชร์ข้ามเครื่องหรือข้ามผู้ใช้ไหม (ถ้าไม่ ใช้ข้อมูลในเครื่องผู้ใช้ได้)
5. ต้นแบบเป็นโอเพนซอร์สหรือไม่ (ถ้าไม่ทราบ สกิลจะตรวจในเฟส 1)

## เฟส 1 — ศึกษาแบบ black-box แล้วเขียนสเปกเชิงหน้าที่

### 1.1 แหล่งที่ใช้ศึกษาได้
- การใช้งานจริงของผู้ใช้ (ผู้ใช้เล่าหรือบรรยายเอง) หรือบัญชีทดลองที่ผู้ใช้มีสิทธิใช้
- เอกสารทางการ คู่มือ หน้าช่วยเหลือ บันทึกการเปลี่ยนแปลง (release notes) วิดีโอสาธิต รีวิว
- มาตรฐานเปิดที่ต้นแบบรองรับ (เช่น รูปแบบไฟล์ CSV, Markdown, iCal)
- **ไม่ใช้**: ซอร์สโค้ดปิดที่หลุดออกมา ไฟล์ที่ได้จากการถอดโค้ด ข้อมูลภายในบริษัท หรือการเข้าส่วนที่ต้องข้าม/หลบการล็อกอิน (ม.30, ม.53/4 [S-01, S-05])
- **ไม่ใช้เป็นข้อมูลนำเข้า**: โค้ด HTML/CSS/JS ข้อความ หรือภาพ ที่ผู้ใช้วางมาหรือดึงจากต้นแบบ (view-source, devtools, "Save page as", คัดลอกจากแอป) ถ้าผู้ใช้วางมา ให้ไม่นำไปใช้ และขอให้บรรยายพฤติกรรมเป็นคำพูดแทน (ม.30, ม.27 [S-01])
- **ภาพหน้าจอ**: ดูได้เพื่อเข้าใจว่าฟีเจอร์ทำอะไรเท่านั้น ห้ามใช้เป็นแบบจำลองหน้าตา ห้ามเก็บลงโปรเจกต์ [S-08]
- แนวปฏิบัติ: บอกผู้ใช้ให้อ่านข้อกำหนดการใช้งาน (ToS) ของต้นแบบ ถ้าห้ามใช้เครื่องมืออัตโนมัติหรือห้ามวิเคราะห์ ให้ศึกษาจากเอกสารสาธารณะเท่านั้น (U-07)

### 1.2 วิธีจด
- จด **พฤติกรรม** ไม่จด **การแสดงออก**: "ผู้ใช้ลากการ์ดไปอีกคอลัมน์ได้ ลำดับถูกบันทึก" แทนการลอกคำอธิบายของเขา (คำสั้นมาตรฐานของ UI เช่น "บันทึก" "ค้นหา" "ลบ" "Undo" ใช้ได้ตามปกติ ที่ห้ามคือข้อความเชิงสร้างสรรค์ เช่น คำอธิบาย ข้อความช่วยเหลือ คำโฆษณา สโลแกน)
- เขียนด้วยคำของตัวเองทั้งหมด ห้ามคัดลอกข้อความ ภาพหน้าจอ ไอคอน หรือคำโฆษณาของต้นแบบลงในสเปก (ภาพหน้าจอถือเป็นส่วนของงานโปรแกรม [S-08]; ข้อความเป็นวรรณกรรม ม.4 [S-01])
- ชื่อเรียกฟีเจอร์ในสเปกใช้คำกลาง ๆ ของเราเอง (เช่น "กระดาน" "การ์ด") ไม่ใช้ชื่อเฉพาะที่ต้นแบบตั้ง (อาจเป็นเครื่องหมายการค้า [S-06])
- ใช้แม่แบบ "สเปกเชิงหน้าที่" ใน `references/templates.md`: ผู้ใช้และเป้าหมาย / ฟีเจอร์ F-01.. / ข้อมูลเข้า-ออก / กฎทางธุรกิจ / กรณีขอบ / สิ่งที่ไม่ทำ
- ทุกฟีเจอร์ต้องมี **เกณฑ์ยอมรับ** ที่ทดสอบได้ (ใช้ในเฟส 5)

### 1.3 ถ้าต้นแบบเป็นโอเพนซอร์ส
บอกผู้ใช้ว่ามี 2 ทาง และให้ผู้ใช้เลือก:

| ทาง | ทำอะไร | หน้าที่ตามสัญญา [S-09, S-10] |
|---|---|---|
| A. fork ตามสัญญา | ใช้โค้ดเขาโดยถูกต้อง แก้ต่อ | MIT: คงประกาศลิขสิทธิ์และข้อความอนุญาต; Apache-2.0: + ระบุการแก้ไข ไม่ได้สิทธิใช้เครื่องหมายการค้า; GPL-3.0: + เปิดซอร์ส ใช้สัญญาเดียวกัน ระบุการแก้ไข; AGPL-3.0: + การให้บริการผ่านเครือข่ายถือเป็นการแจกจ่าย |
| B. เขียนใหม่แบบ clean-room | ทำตามสกิลนี้ ไม่เปิดดูโค้ดเขาระหว่างเขียน | ไม่มีหน้าที่ตามสัญญาของเขา แต่ยังต้องไม่ใช้ชื่อ/โลโก้ |

ข้อควรระวัง: ถ้าเลือกทาง B ห้ามผสมโค้ดที่ลอกจากซอร์สเขาเข้ามา เพราะจะกลายเป็นการดัดแปลงที่ต้องทำตามสัญญา (ม.4 "ดัดแปลง", ม.30 [S-01])
ถ้าทาง A ไม่ใช่สัญญา MIT/Apache/GPL/AGPL ให้บอกว่าสกิลไม่ได้ตรวจสัญญานั้น ให้ผู้ใช้อ่านตัวสัญญาเอง

## เฟส 2 — ประเมินความเป็นไปได้

จัดทุกฟีเจอร์ในสเปกลงตาราง (แม่แบบใน `references/templates.md`):

| ประเภท | ความหมาย | ตัวอย่าง |
|---|---|---|
| **เบราว์เซอร์ล้วน** | ทำได้ด้วย HTML/CSS/JS ข้อมูลอยู่ใน `localStorage`/IndexedDB ของผู้ใช้ | จับเวลา จดโน้ต คำนวณ ส่งออก/นำเข้าไฟล์ |
| **ต้องมีเซิร์ฟเวอร์** | ต้องแชร์ข้อมูลข้ามคนหรือข้ามเครื่อง ต้องเก็บความลับ ต้องทำงานตามเวลาแม้ปิดเบราว์เซอร์ | ซิงก์ แชร์ลิงก์ แจ้งเตือนทางอีเมล ระบบบัญชีผู้ใช้ |
| **ต้องใช้ API ภายนอก** | ต้องพึ่งบริการคนอื่น ระบุ: ผู้ให้บริการ ค่าใช้จ่ายโดยประมาณ (ถ้าไม่ทราบให้เขียน "ต้องตรวจราคา") เงื่อนไขการใช้ ขีดจำกัด | แผนที่ ชำระเงิน แปลภาษา AI |
| **ทำไม่ได้/ไม่ควรทำ** | ผิดเฟส 0.2 หรือเกินกำลัง | เข้าระบบของต้นแบบ ดูดข้อมูลของเขา ใช้ไฟล์ของเขา |

แล้วทำตาราง **MVP vs ภายหลัง**:
- MVP = ฟีเจอร์ที่ทำให้แอปใช้งานได้จริงตามเป้าหมายหลัก และส่วนใหญ่เป็น "เบราว์เซอร์ล้วน"
- ภายหลัง = ต้องเซิร์ฟเวอร์ ต้องจ่ายเงิน หรือไม่จำเป็นต่อการใช้งานแรก
- ระบุความเสี่ยง (เช่น ข้อมูลหายถ้าล้างเบราว์เซอร์ → แก้ด้วยปุ่มส่งออกไฟล์สำรอง)

ถามผู้ใช้ยืนยัน MVP ก่อนเฟส 3

## เฟส 3 — ออกแบบของตัวเอง

### 3.1 เอกลักษณ์ใหม่
- **ชื่อใหม่** — *ข้อบังคับ (คำแปล)*: ไม่เหมือนหรือคล้ายจนสาธารณชนสับสนว่าเป็นของเจ้าของต้นแบบ [S-06 ม.109, ม.46 วรรคสอง] — *แนวปฏิบัติ*: ไม่มีชื่อต้นแบบเป็นส่วนของชื่อ ไม่เติมคำหน้า/หลังชื่อเขา (เช่น "X Lite", "X ไทย") และเสนอชื่อ 3–5 ชื่อ ให้ผู้ใช้ค้นในฐานข้อมูลเครื่องหมายการค้าของกรมทรัพย์สินทางปัญญาเองก่อนใช้จริง (สกิลค้นแทนไม่ได้)
- **ไอคอน/โลโก้ใหม่** — *ข้อบังคับ*: ออกแบบเองหรือใช้ชุดไอคอนเสรีตามสัญญา ห้ามคัดลอกหรือวาดเลียนโลโก้/ไอคอนเขา (ศิลปกรรม ม.4, ม.27 [S-01]; โลโก้ที่จดทะเบียน ม.109 [S-06, คำแปล])
- **ข้อความในแอป** — *ข้อบังคับ*: เขียนข้อความเชิงสร้างสรรค์ใหม่ทั้งหมด ไม่แปลข้อความของต้นแบบมาใช้ (การแปลวรรณกรรมเป็นการดัดแปลง ม.4 "ดัดแปลง" (1) [S-01]) คำสั้นมาตรฐานของ UI ใช้ได้
- **สีและฟอนต์ใหม่** — *แนวปฏิบัติ*: ไม่ใช้ชุดสีหลักเดียวกับต้นแบบ ฟอนต์ใช้ฟอนต์เสรีตามสัญญาของแต่ละฟอนต์ (ตัวไฟล์ฟอนต์ของต้นแบบห้ามใช้ = ข้อบังคับ C-03)
- **เลย์เอาต์** — *แนวปฏิบัติ*: เลย์เอาต์ทั่วไปของประเภทแอป (เช่น แถบด้านซ้าย + พื้นที่หลัก) ใช้ได้ แต่ **ไม่จัดทุกองค์ประกอบให้เหมือนต้นแบบจนดูเป็นแอปเดียวกัน** (กฎหมายไทยเรื่อง trade dress ของซอฟต์แวร์ยืนยันไม่ได้ ดู U-04)

### 3.2 สถาปัตยกรรมและโครงไฟล์ (ค่าเริ่มต้น)
- หน้าเดียว (single page) HTML + CSS + JavaScript ธรรมดา ไม่ต้อง build ไม่ต้องติดตั้ง เปิดไฟล์ `index.html` ได้เลย
- ข้อมูลอยู่ในเครื่องผู้ใช้ (`localStorage` สำหรับข้อมูลเล็ก, IndexedDB ถ้าใหญ่) พร้อมปุ่มส่งออก/นำเข้า JSON
- ถ้าเฟส 2 สรุปว่าต้องมีเซิร์ฟเวอร์ ให้เสนอทางเลือกแบบง่ายก่อน (เช่น ให้ผู้ใช้ส่งไฟล์กันเอง) แล้วค่อยเสนอเซิร์ฟเวอร์เป็นงานภายหลัง

```
my-app/
├── index.html        # โครงหน้า
├── style.css         # สีและเลย์เอาต์ของเราเอง
├── app.js            # ตรรกะ แยกฟังก์ชันตามฟีเจอร์ F-xx
├── assets/           # ไอคอนที่ออกแบบเอง หรือไอคอนเสรี + ไฟล์สัญญา
├── docs/             # spec.md feasibility.md design.md test-report.md
├── README.md
└── LICENSE
```

บันทึกการออกแบบลง `docs/design.md` ตามแม่แบบ

## เฟส 4 — สร้าง

- เขียนโค้ดใหม่จากสเปกของเราเท่านั้น ไม่เปิดดูซอร์สของต้นแบบระหว่างเขียน (แนวปฏิบัติ clean-room; ทำให้ชัดว่าไม่ใช่การทำซ้ำ/ดัดแปลง ตามนิยาม ม.4 ที่ใช้คำว่า "โดยไม่มีลักษณะเป็นการจัดทำงานขึ้นใหม่" [S-01])
- คอมเมนต์โค้ดเป็นภาษาไทยหรืออังกฤษตามที่ผู้ใช้ต้องการ ใส่รหัสฟีเจอร์ (`// F-03: ลากการ์ดข้ามคอลัมน์`) เพื่อโยงกับสเปก
- ไลบรารีโอเพนซอร์สใช้ได้ โดย:
  - ตรวจสัญญาอนุญาตก่อนใช้ ชอบ MIT/Apache-2.0 สำหรับแอปที่อาจปิดซอร์สหรือขาย; ถ้าใช้ GPL/AGPL ต้องบอกผู้ใช้ว่ามีหน้าที่เปิดซอร์ส [S-10]
  - คงประกาศลิขสิทธิ์ของไลบรารีไว้ และใส่เครดิตใน README [S-09]
  - โหลดจาก CDN ที่ระบุเวอร์ชันแน่นอน หรือเก็บไฟล์ไว้ในโปรเจกต์
- ห้ามเรียก API ภายในที่ไม่ได้เปิดสาธารณะของต้นแบบ ห้ามฝังเนื้อหาของเขา (iframe/hotlink รูป) เพื่อทำเป็นของเรา (แนวปฏิบัติ; เนื้อหาเป็นงานอันมีลิขสิทธิ์ ม.27 [S-01])
- ความปลอดภัยพื้นฐาน: escape ข้อความที่ผู้ใช้กรอกก่อนแสดง (ใช้ `textContent` ไม่ใช้ `innerHTML` กับข้อมูลผู้ใช้) ไม่เก็บรหัสผ่านใน `localStorage`

## เฟส 5 — ทดสอบ

1. **เทียบสเปกข้อต่อข้อ**: ทุก F-xx มีผล ผ่าน / ไม่ผ่าน / ยังไม่ทำ (พร้อมเหตุผล) ตามเกณฑ์ยอมรับในสเปก
2. **เบราว์เซอร์**: Chrome/Edge และ Firefox อย่างน้อย; Safari ถ้ามี
3. **มือถือ**: ความกว้าง ~375px ไม่มีแถบเลื่อนแนวนอน ปุ่มกดง่าย (อย่างน้อยประมาณ 44px)
4. **คีย์บอร์ดและการเข้าถึง**: ใช้งานทุกฟีเจอร์ได้ด้วยคีย์บอร์ด (Tab ไปถึงทุกปุ่ม เห็นกรอบโฟกัส Enter/Space กดได้ Esc ปิดหน้าต่าง) ฟีเจอร์ที่ใช้การลากต้องมีทางเลือกที่ไม่ต้องลาก; ความต่างของสีข้อความกับพื้นหลังผ่านเกณฑ์ WCAG AA (ประมาณ 4.5:1 สำหรับข้อความปกติ) และไม่สื่อความหมายด้วยสีอย่างเดียว
5. **กรณีขอบ**: ข้อมูลว่าง ข้อความยาวมาก ภาษาไทยปนอังกฤษและอีโมจิ ข้อมูลจำนวนมาก รีเฟรชกลางทาง ล้างที่เก็บข้อมูล นำเข้าไฟล์เสีย
6. **ข้อมูล**: ปิดแล้วเปิดใหม่ข้อมูลยังอยู่; ส่งออกแล้วนำเข้ากลับได้ครบ
7. ถ้าเซสชันมีเครื่องมือเปิดเบราว์เซอร์ ให้เปิดทดสอบจริงและจับภาพหน้าจอแอป **ของเรา** แนบรายงาน ถ้าไม่มี ให้เขียนขั้นตอนทดสอบด้วยมือให้ผู้ใช้

บันทึกลง `docs/test-report.md`

README ต้องมี:

   - เขียนใหม่ทั้งหมด ไม่มีโค้ด ข้อความ ภาพ หรือไฟล์ของ X
   - ตารางความแตกต่าง (ชื่อ หน้าตา ฟีเจอร์ที่มี/ไม่มี เทคโนโลยี)

4. **เครดิตไลบรารี/ฟอนต์/ไอคอน** ชื่อ เวอร์ชัน สัญญา ลิงก์
5. ข้อจำกัดที่ทราบ และรายการ "ภายหลัง" จากเฟส 2
6. วันที่ตรวจกฎหมาย 2026-11-10 และคำเตือนว่าไม่ใช่คำปรึกษากฎหมาย

## สิ่งที่สกิลนี้ไม่ทำ
- ไม่ถอดโค้ด (decompile/disassemble) ไม่ดูซอร์สปิดที่หลุด
- ไม่เจาะระบบ ไม่หลบเลี่ยง DRM ไม่ข้ามล็อกอิน ไม่ดูดข้อมูล
- ไม่สร้างหน้าเลียนแบบเพื่อหลอกให้กรอกข้อมูล ไม่สร้างแอปปลอมแบรนด์
- ไม่รับรองผลทางกฎหมาย ไม่ค้นฐานเครื่องหมายการค้าแทนผู้ใช้

## คำเตือน (บอกผู้ใช้ทุกครั้งที่ส่งมอบ)
- สกิลนี้ **ไม่ใช่คำปรึกษาทางกฎหมาย** เป็นเพียงกระบวนการที่ช่วยลดความเสี่ยง
- กฎหมายแต่ละประเทศต่างกัน สกิลอ้างกฎหมายไทยเป็นหลักและแหล่งสหรัฐฯ เพื่อเทียบหลักการ ถ้าจะเผยแพร่หรือขายในประเทศอื่นให้ตรวจกฎหมายประเทศนั้น
- ถ้าจะทำเชิงพาณิชย์ ระดมทุน หรือใช้ชื่อเป็นแบรนด์ ควรปรึกษาทนายความหรือผู้เชี่ยวชาญทรัพย์สินทางปัญญา
- แหล่งตรวจเมื่อ **2026-11-10** กฎหมายอาจถูกแก้ไขหลังจากนั้น; แหล่งเครื่องหมายการค้าเป็นคำแปลไม่เป็นทางการ (S-06)
- ข้อกำหนดการใช้งานของต้นแบบเป็นสัญญาแยกต่างหาก อาจห้ามบางอย่างเพิ่มเติม ผู้ใช้ต้องอ่านเอง
